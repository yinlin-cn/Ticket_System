# 服务端架构

## 1. 分层

服务端分为框架层和业务层。

```text
framework/
  连接管理、Reactor、分帧、短任务、DB 协程、发送、错误和指标

app/
  TicketService、ConnectionRoster、OrderEngine、RedisClient、CacheModule、Password
```

框架不包含票务规则，业务层不接管 epoll、socket 生命周期和框架工作线程。

## 2. 框架层

### 2.1 接入

服务入口创建框架实例：

```cpp
Server server(callback, 9101, 8, 16, 4);
```

参数依次表示端口、解析线程数、业务线程数和 Reactor 线程数。框架通过
`mark_fast_prefix` 和 `mark_db_prefix` 把命令划入快速短任务或数据库协程路径。

### 2.2 连接视图

框架中的连接标识是虚拟 FD，用于网络调度和发送，不等同于账号身份。业务层只把
它作为当前离线连接的句柄，并同时持有可探测连接是否仍有效的弱连接对象。

### 2.3 分帧与发送

框架负责长度帧解析。业务层拿到的是一条完整帧体。发送经过框架发送队列和批发送
机制，业务代码调用 `send` 不等于每次立即执行一次 socket `write`。

### 2.4 错误和指标

框架提供统一错误处理入口。业务层把可预期错误转换为协议错误码，把未知错误交给
框架错误处理器记录并返回 `INTERNAL`。

## 3. 业务入口

`TicketService::handle` 是统一命令入口。

| 类别 | 命令 |
| --- | --- |
| 心跳与身份 | `ping`、`whoami`、`logout` |
| 账号 | `register`、`login`、`login.challenge`、`login.proof` |
| 商品 | `catalog.list` |
| 订单 | `order.reserve`、`order.status`、`order.my` |
| 退款 | `refund.submit` |
| 通知 | `notice.push` |

入口遵循以下顺序：

1. 去掉命令前缀并拆分参数。
2. 校验参数格式和范围。
3. 从连接名册解析账号身份。
4. 必要时执行兼容 token 鉴权。
5. 执行短查询或把长任务提交给业务队列。

## 4. 连接身份与鉴权

### 4.1 两层映射

```text
virtual_fd -> RosterIdentity
identity_id -> virtual_fd
```

虚拟 FD 是连接级标识，`identity_id` 是账号级标识。异步订单结果必须在投递时
重新解析连接，不能永久保存虚拟 FD。

### 4.2 挑战式登录

```text
login.challenge|username
  -> nonce + salt

client:
  key   = PBKDF2-HMAC-SHA256(password, salt, 120000, 256)
  proof = HMAC-SHA256(key, nonce)

login.proof|username|proof
  -> token + user_id
```

挑战保存在进程内，有效期 30 秒且只能使用一次。未知账号也返回随机 salt，
以降低账号枚举的时序差异。连续失败会触发账号短期锁定。

### 4.3 在线约束

一个账号同一时刻只允许一条在线业务连接。重复登录返回 `ALREADY_ONLINE`。
登出、断线或心跳超时后，名册通过框架连接变更通知和周期对账清理身份。

## 5. 商品与缓存

`catalog.list` 先查 `CacheModule`，缓存完整时直接返回；缺失时通过框架 DB 协程
回源 MariaDB，再更新缓存。

缓存特性：

- 固定最大容量，默认 4096 项。
- LRU 淘汰。
- 每个值带 TTL。
- 读取时惰性检查过期。
- 商品展示允许短时间快照延迟。

主要键：

```text
catalog:types
catalog:item:<ticket_type_id>
catalog:price:<ticket_type_id>
stock:<ticket_type_id>
```

缓存不是事实来源。最终库存仍由 MariaDB 条件更新决定。

## 6. Redis 准入

开启 `TICKET_ADMISSION_REDIS=1` 时，购票入口用 Lua 原子完成：

1. 检查用户幂等键。
2. 检查库存是否足够。
3. 扣减 Redis 可准入库存。
4. 记录幂等键到订单号映射。

库存不足返回 `SOLD_OUT`，重复请求返回 `DUPLICATE`，库存键不存在返回
`NOT_READY`，Redis 操作失败返回 `REDIS_ERROR`。

Redis 库存是“还能允许多少票进入数据库事务”，数据库库存是“最终还剩多少票”。
`admitted_units_` 记录已准入但尚未完成数据库处理的数量，用于计算批处理预算。

关闭 Redis 时，请求直接进入业务队列，最终靠数据库条件更新防超卖。该模式少了
一次网络往返，但入口没有前置幂等拦截，重复请求可能浪费一次库存扣减。

## 7. OrderEngine

### 7.1 队列

每个票种维护：

```text
购票队列
退款队列
in_flight 状态
重试次数
重试时间
```

不同票种互相独立，同一票种同一时刻只推进一个批次。退款先于购票。

### 7.2 调度

调度线程按 `tick_ms` 扫描票种，读取缓存中的库存和价格，再按额度切出一批任务。
任务移出业务队列后，通过内部队列交给专用 worker。

### 7.3 事务

购票事务执行条件库存更新和多值订单插入。退款事务同时校验订单归属、票种、状态、
可退数量和幂等键，再更新退款记录、订单退款数量和库存。

### 7.4 失败处理

- 业务拒绝生成最终错误结果。
- 系统错误按上限重试。
- 超过重试上限后生成最终失败结果。
- 购票失败时补偿已经预扣的 Redis 准入量。
- 售罄时把本批和该票种后续队列中无法满足的订单全部判为失败。

### 7.5 队列长度与内存

当前业务队列没有独立硬容量或高低水位。开启 Redis 时库存闸门限制了有效订单的
上限；长期关闭 Redis 且入口流量远高于数据库处理速度时，队列仍可能持续增长。

## 8. 异步结果投递

最终结果通过 `ConnectionRoster` 按 `identity_id` 投递。投递策略：

1. 原连接仍有效时优先使用原连接。
2. 原连接失效时查找同一账号的当前在线连接。
3. 账号不在线时不发送给其他账号。

当前版本没有独立离线结果持久化队列，因此不保证账号离线后的稍后补发。

## 9. 背压与并发

现有背压来自多层：

- 框架网络读取和发送队列。
- 框架数据库连接与 worker 准入。
- Redis 库存闸门。
- 每票种 `in_flight` 串行推进。
- `batch_max` 限制单批大小。
- 客户端出站队列和协议超时。

这不是单一队列的背压，而是从网络、准入、业务队列、数据库连接和客户端窗口
共同形成的链式约束。

## 10. 扩展边界

新增短查询：

1. 在 `main.cpp` 标记为 DB 路由。
2. 在 `TicketService` 中解析并执行单次 SQL。
3. 对不带写事务的响应直接回送。

新增长事务：

1. 在 `main.cpp` 标记为 Fast 路由。
2. 入口只做校验和准入。
3. 构造独立队列项并提交给业务线程池。
4. 通过 `ConnectionRoster` 异步回送。
5. 明确重试、补偿和最终错误语义。

不要：

- 在框架业务线程中等待 `OrderEngine`。
- 把 `queued` 当作最终成功。
- 在队列项中长期保存裸 socket。
- 用缓存值代替数据库条件更新。
- 只做 Redis 幂等而不做数据库唯一约束。
