# 总体架构

## 1. 设计目标

系统围绕一条高并发票务链路设计：

```text
连接 -> 鉴权 -> 商品浏览 -> 抢票受理 -> 事务落库 -> 结果回送
```

核心目标是：

1. 网络层不被数据库事务拖死。
2. 短查询和长事务互不占用同一组数据库额度。
3. 热门票种内部减少同一库存行的并发竞争。
4. 客户端断开或重连后，异步结果仍能按账号身份投递。
5. 入口先做低成本准入，避免大量无效请求进入数据库。
6. 客户端业务通过任务插槽组织，避免全部逻辑堆进一个窗口类。

## 2. 系统分层

```text
表现层
  Java Swing 页面
    只渲染状态、收集输入、提交事件

客户端应用层
  LongTaskRuntime / ClientTask
    组织业务事件和页面切换

客户端通信层
  ProtocolWorker / NetworkClient
    长度帧、请求匹配、读写线程和心跳

服务端接入层
  Reactor / Parser / FrameworkCall
    epoll、连接视图、帧解析和短任务调度

服务端业务层
  TicketService / ConnectionRoster
    命令分发、身份、鉴权、商品和业务入口

异步订单层
  OrderEngine
    按票种队列、批处理、事务、重试和结果生成

数据层
  Redis / MariaDB / CacheModule
    准入与幂等、最终事实、读快照
```

每一层只依赖相邻层的明确接口。页面不直接访问 Socket，业务层不直接控制框架
工作线程，异步队列不长期持有裸 socket。

## 3. 完整请求链路

### 3.1 短查询

```text
客户端
  -> 长度帧
  -> 框架 Parser
  -> 框架 DB 路由
  -> TicketService
  -> 框架 DB 协程
  -> MariaDB
  -> 框架发送队列
  -> 客户端
```

适用于注册、登录、商品列表、订单状态和个人订单查询。

### 3.2 购票

```text
客户端 order.reserve
  -> 框架快速路由
  -> TicketService 校验身份和参数
  -> 生成订单号
  -> Redis Lua 原子检查幂等键并预扣库存
  -> 同步返回 reserve|queued
  -> PendingOrder 进入票种队列
  -> OrderEngine 调度批次
  -> 独立数据库 worker 执行事务
  -> 更新库存、缓存和 Redis
  -> ConnectionRoster 按 identity_id 投递最终结果
```

`queued` 只代表任务已受理，最终结果由 `reserve.result` 表示。

### 3.3 退票

```text
客户端 refund.submit
  -> 框架快速路由
  -> TicketService 校验身份和参数
  -> PendingRefund 进入对应票种退款队列
  -> 同步返回 refund|queued
  -> OrderEngine 优先处理退款
  -> 校验订单归属、票种、状态和可退数量
  -> 更新退款记录、订单退款数量与库存
  -> 异步返回 refund.result
```

同一票种先处理退款，再处理购票，使恢复的库存能参与下一批预算。

## 4. 两条数据库路径

### 4.1 框架数据库路径

特点：

- 单次或少量 SQL。
- 使用框架数据库协程。
- 受框架 DB 连接数和 worker 数限制。
- 不在协程里等待业务队列或外部事件。

默认配置为 20 个连接、20 个 worker。

### 4.2 业务独立数据库路径

特点：

- 需要事务、批处理或重试。
- 使用 `OrderEngine` 自己的连接池和线程池。
- 不受框架 DB 准入额度影响。
- 同一票种通过 `in_flight` 串行推进一个批次。

默认配置为 8 个连接、6 个 worker、单批最多 500 项、2ms 扫描周期。

这两条路径分开后，商品查询高峰不会直接卡住订单落库，订单事务也不会长期占用
框架业务线程。

## 5. 数据职责

| 数据 | 事实来源 | 加速或协调层 |
| --- | --- | --- |
| 用户和密码 | MariaDB | 无 |
| 商品和价格 | MariaDB | `CacheModule` |
| 最终库存 | MariaDB | Redis 准入值、缓存快照 |
| 订单 | MariaDB | 无 |
| 退款 | MariaDB | 无 |
| 用户幂等状态 | Redis 短期记录 | MariaDB 唯一键兜底 |
| 在线身份 | 进程内 `ConnectionRoster` | 框架连接变更通知 |

不能把缓存或 Redis 当作订单最终账本。缓存命中只减少读库，Redis 准入只减少无效
数据库请求，最终结果仍由 MariaDB 事务决定。

## 6. 关键一致性策略

### 6.1 幂等

- 订单表对 `(user_id, idempotency_key)` 建唯一约束。
- 退款表对 `(user_id, request_id)` 建唯一约束。
- Redis 在开启准入时提前拦截重复请求。
- 关闭 Redis 后，数据库唯一约束仍负责最终防重。

### 6.2 防超卖

数据库更新使用条件语句：

```sql
UPDATE ticket_inventory
SET remaining_qty = remaining_qty - ?
WHERE ticket_type_id = ? AND remaining_qty >= ?;
```

只有更新影响行数满足要求时才插入订单，库存更新和订单插入在同一事务中完成。

### 6.3 连接身份

异步结果记录 `identity_id`，不依赖提交时的虚拟 FD 永久有效。投递时先尝试原
连接，再查找同一账号当前在线连接。账号离线时当前版本不保证补发。

## 7. 并发模型

服务端大致包含以下并发角色：

| 角色 | 数量与职责 |
| --- | --- |
| Reactor | 处理 epoll 和连接事件 |
| Parser | 解析长度帧并生成任务 |
| 框架业务 worker | 执行短任务 |
| 框架 DB worker | 执行查询协程 |
| `OrderEngine` 调度线程 | 扫描票种队列、切片和分配批次 |
| `OrderEngine` worker | 执行购票与退款事务 |
| `ConnectionRoster` | 处理连接变更并投递结果 |

同票种串行、跨票种并行的目的是减少同库存行的锁竞争，同时保留不同商品之间的
并行度。

## 8. 客户端组织

客户端采用五类角色：

| 角色 | 职责 |
| --- | --- |
| Swing EDT | 只操作界面 |
| `FrontendSlot` | 页面提交事件的统一入口 |
| `LongTaskRuntime` | 单线程执行客户端业务任务 |
| `NetworkClient` | 独立读写线程和心跳 |
| `ProtocolWorker` | 请求登记、响应匹配和超时 |

页面、任务、协议和网络职责分开后，新增业务主要增加页面、任务和状态，不需要
修改网络线程。

## 9. 设计取舍

### 9.1 为什么不让订单入口直接查数据库

订单入口如果同步等待事务，会长期占用框架业务线程。高并发时线程池和数据库连接
很快被耗尽，登录和商品查询也会受到连带影响。

### 9.2 为什么按票种拆队列

所有订单共用一个队列会让不同库存行互相阻塞，也难以控制同一库存行的并发竞争。
按票种拆队列后，同一票种串行推进，不同票种独立使用 worker 和数据库连接。

### 9.3 为什么不把 Redis 当最终库存

Redis 适合快速准入、幂等和协调，但订单、退款和库存账本需要数据库事务、唯一
约束和可查询状态。最终事实仍保存在 MariaDB。

### 9.4 为什么客户端不把所有业务放进一个窗口类

票务客户端包含连接、认证、商品、订单、退款和日志等不同状态。任务插槽把业务
副作用与 Swing 页面分开，便于增加页面、替换界面和单独测试任务。

## 10. 当前边界

- 单进程会话和连接名册。
- 明文 TCP，没有 TLS。
- 一个账号只允许一个在线业务连接。
- 订单业务队列没有独立硬容量。
- 没有真实支付、超时释放库存和运营后台。
- 账号离线时不保证异步结果补发。

这些限制已经明确写入各模块文档，后续扩展应优先补可靠异步、入口背压、安全和
多实例一致性。
